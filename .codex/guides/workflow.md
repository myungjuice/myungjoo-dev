# 작업 흐름 가이드

## 전체 흐름

개발 작업은 다음 순서로 진행한다.

1. 요청을 읽기 전용 질문·진단과 파일·Git·외부 상태를 바꾸는 개발 작업으로 분류한다.
2. 작업 요청과 연결된 GitHub 이슈를 확인한다. 연결 이슈가 없으면 등록 여부를 질문하고,
   사용자가 원할 때 목적, 배경, 완료 조건을 담은 한글 초안과 라벨을 제시한 뒤 승인 후
   생성한다.
3. 오케스트레이션 skill의 난이도·범위·위험도 최댓값 기준으로 초기 등급을 판정하고 필요한
   역할, 독립성, 승인 경계, 품질 gate를 정한다.
4. 작업 유형에 필요한 Superpowers를 사용해 요구사항과 제약을 정리한다.
5. 스펙과 계획, 실행 방식의 권장안·근거·영향 범위를 제시하고 사용자 승인을 받는다. 이미
   승인된 동일 범위의 스펙과 계획은 반복해서 질문하지 않는다.
6. 구현 직전에 실제 설계와 테스트 범위로 등급을 다시 판정한다. 승인 범위를 벗어난 새
   영향이 있으면 구현을 멈추고 재승인받는다.
7. 기능·버그 구현은 의도한 이유로 실패하는 테스트를 먼저 확인하고 최소 구현과
   리팩터링을 진행한다.
8. 등급과 작업 유형에 맞는 QA가 완료 조건과 실제 사용자 동작을 검증한다.
9. 최종 diff를 기준으로 리뷰 직전 등급을 다시 판정한다.
10. 프로덕션 코드는 구현자와 독립된 Code Reviewer의 검토를 받는다.
11. 관련 검증을 좁은 범위부터 확장하고 최종적으로 `pnpm verify`를 실행한다.
12. 검증과 리뷰 결과를 보고한 뒤 push, Draft PR, Ready, 병합 등 GitHub 변경의 별도 승인
    경계를 따른다.

세부 등급, 역할 routing, 품질 증거, handoff 형식은
`.agents/skills/orchestrating-myungjoo-development/`를 따른다.

## 이슈 형식

- 이슈 제목은 `[feat] 기능명`, `[fix] 버그명`처럼 영문 타입과 한글 설명을 사용한다.
- 이슈 타입은 `feat`, `fix`, `refactor`, `chore`, `docs`, `style`, `perf` 중 작업 목적에 맞게 선택한다.
- 이슈 본문은 기획 관점에서 무엇을 만들지, 왜 필요한지, 어떤 결과가 완료 조건인지 설명한다.
- 개발 구현 내역과 변경 파일 목록은 이슈가 아니라 PR 본문에 작성한다.
- 이슈의 제목, 본문, 답변은 한글로 작성한다.

## Superpowers 작업 흐름

기능, 버그 수정, 리팩터링처럼 구현이 필요한 작업은 전체 흐름 안에서 다음 원칙을 지킨다.

1. 브레인스토밍으로 요구사항, 제약, 완료 조건을 정리한다.
2. 스펙과 계획을 로컬 작업 문서로 작성하고 사용자 검토를 받는다.
3. 규모와 의존성을 판단해 inline 실행과 `subagent-driven` 실행을 비교한다.
4. 권장 방식, 근거, 작업 영향 범위를 제시하고 사용자 승인 후 실행한다.
5. 기능·버그 구현은 테스트 우선으로 진행하고, 완료 주장 전 최신 검증 증거를 확인한다.

## HTML 시각화 제안

다음 조건 중 하나에 해당하면 HTML 시각화가 도움이 되는지 판단해 사용자에게 제안한다.

- 여러 화면이나 상태 전환이 있는 사용자 흐름
- 사용자 경험이나 시각 디자인이 중요한 기능
- 선택 가능한 레이아웃·정보 구조·상호작용 대안이 둘 이상인 작업

사용자가 승인하면 로컬 서버에서 2~3개 시안을 준비해 보여주고 선택받는다. 단순 텍스트 수정, 문서 작업, 국소 버그 수정처럼 시각화 이점이 작으면 이 단계를 생략한다.

## 반드시 승인할 결정

다음은 구현 또는 실행 전에 선택지, 권장안, 영향 범위를 제시하고 승인받는다.

- 사용자 동작, 데이터 구조, 화면 설계의 변경
- 의존성 추가·업데이트
- 빌드·배포 설정 변경
- inline 실행과 `subagent-driven` 실행의 선택
- HTML 시각화와 시안 작성
- 이슈 생성, PR 생성, 직접 푸시, 병합, 태그, GitHub Release 생성

이미 승인된 스펙·계획과 동일한 범위는 다시 승인받지 않는다. 다만 새 의존성, 외부 계약,
사용자 동작, 데이터 구조, 화면 설계, 보안·배포 영향처럼 승인 경계가 달라지면 작업을
멈추고 새 영향 범위에 대해 승인받는다.
