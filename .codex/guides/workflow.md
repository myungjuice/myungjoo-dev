# 작업 흐름 가이드

## 시작 절차

1. 작업 요청과 연결된 GitHub 이슈를 확인한다.
2. 연결 이슈가 없으면 이슈 등록 여부를 질문한다.
3. 사용자가 이슈 등록을 원하면 목적, 배경, 완료 조건을 담은 한글 초안과 라벨을 먼저 제시한다.
4. 사용자 승인 후에만 이슈를 생성한다.

## 이슈 형식

- 이슈 제목은 `[feat] 기능명`, `[fix] 버그명`처럼 영문 타입과 한글 설명을 사용한다.
- 이슈 타입은 `feat`, `fix`, `refactor`, `chore`, `docs`, `style`, `perf` 중 작업 목적에 맞게 선택한다.
- 이슈 본문은 기획 관점에서 무엇을 만들지, 왜 필요한지, 어떤 결과가 완료 조건인지 설명한다.
- 개발 구현 내역과 변경 파일 목록은 이슈가 아니라 PR 본문에 작성한다.
- 이슈의 제목, 본문, 답변은 한글로 작성한다.

## Superpowers 작업 흐름

기능, 버그 수정, 리팩터링처럼 구현이 필요한 작업은 다음 순서를 따른다.

1. 브레인스토밍으로 요구사항, 제약, 완료 조건을 정리한다.
2. 스펙과 계획을 로컬 작업 문서로 작성하고 사용자 검토를 받는다.
3. 규모와 의존성을 판단해 inline 실행과 `subagent-driven` 실행을 비교한다.
4. 권장 방식, 근거, 작업 영향 범위를 제시하고 사용자 승인 후 실행한다.
5. 구현, 테스트, 코드 리뷰, GitHub 변경을 순서대로 수행한다.

## HTML 시각화 제안

다음 조건 중 하나에 해당하면 HTML 시각화가 도움이 되는지 판단해 사용자에게 제안한다.

- 여러 화면이나 상태 전환이 있는 사용자 흐름
- 사용자 경험이나 시각 디자인이 중요한 기능
- 선택 가능한 레이아웃·정보 구조·상호작용 대안이 둘 이상인 작업

사용자가 승인하면 로컬 서버에서 2~3개 시안을 준비해 보여주고 선택받는다. 단순 텍스트 수정, 문서 작업, 국소 버그 수정처럼 시각화 이점이 작으면 이 단계를 생략한다.

## 반드시 승인할 결정

다음은 구현 또는 실행 전에 선택지, 권장안, 영향 범위를 제시하고 승인받는다.

- 사용자 동작, 데이터 구조, 화면 설계의 변경
- 의존성 추가·업데이트
- 빌드·배포 설정 변경
- inline 실행과 `subagent-driven` 실행의 선택
- HTML 시각화와 시안 작성
- 이슈 생성, PR 생성, 직접 푸시, 병합, 태그, GitHub Release 생성
